# Original commerce notification settings APIs

POST `/vendor-console/integration/shopify/update-notification-settings` and POST `/vendor-console/integration/woocommerce/update-notification-settings` now have partial adapters. Use native bearer/workspace authentication, `vendor.integrations.manage` and an `Idempotency-Key` of 8?100 letters, digits, underscores or hyphens. Optional query `integration_id` selects an owned store; multiple stores require selection. Optional body `phone_number_id` selects an owned connected WhatsApp sender. Without it, reuse the store's native sender or select the sole connected sender; ambiguity fails.

The original body contains unique `notification_types`, `template_uid` keyed by notification type and numbered variable mappings. Shopify uses a JSON string `variable_mappings`; WooCommerce uses an object `variable_mapping`. Only selected types may have mappings. Every selected type needs an owned approved template UUID. Numbered variables must match the approved component schema; body/header variables sharing a number intentionally share the original mapping. Static templates need no variables. Empty selected types disable rules, including when the previously configured sender has disconnected. Enabling or changing the sender still requires a connected owned credential.

Supported order field aliases are `order_number`, `order_id`, `order_total`/`total_price`, `order_status`/`status`, `currency`, `customer_name` and Shopify `tracking_number`/`tracking_url`. They become native order-field values with the existing '-' fallback. Unsupported address/date/payment/company/COD fields and WooCommerce tracking mappings fail explicitly rather than silently producing incorrect values.

Shopify supports confirmation, payment, shipment, cancellation and refund rules. WooCommerce supports confirmation, payment, processing, completed, on-hold, cancellation, refund and failure rules. Delivery confirmation/COD verification and other types without their provider event workflow fail explicitly. Legacy media/dynamic URL/coupon mappings require native rich-template settings; named or unsupported components cannot be saved through this adapter.

The shared native write service checks current integration permission, locks the store, validates its sender and approved template components, preserves native metadata and commits configuration/audit together. Malformed imported store metadata requires reconciliation. Legacy translation and idempotency use a serializable transaction. Success retains `{success:true,message:"Notification settings updated successfully"}`; replay avoids further writes/audits, and a changed request with the same key conflicts. The native PUT endpoint retains HTTP 204 and uses the same validation/write transaction. Configuration does not send provider messages.

Original multipart/browser/session contracts, sender-session selection, legacy setting storage/import activation, all notification triggers/field formats/rich templates, billing policies, translations/errors and live provider/source comparison remain pending. These are partial adapters, not verified full frontend or provider parity.
