# Native custom-field definitions

`/api/v1/vendors/:vendorId/custom-fields` provides paginated GET, POST, GET/PATCH/DELETE `/:id`. The previous `/resources/custom-fields` path uses the same dedicated router. Generic resource writes are disabled so they cannot bypass these rules.

Reads require `vendor.contacts.view`; mutations require `vendor.contacts.edit`. POST accepts `inputName`, supported `inputType` and optional display `name`. Native names are safe CSV/template identifiers, at most 64 characters, with exact business-local uniqueness. Reserved/internal names and unsupported types are rejected. A vendor definition lock serializes duplicate names and the native 100-field limit across both route aliases. This limit is a native implementation bound, not a verified subscription-plan entitlement.

PATCH requires the current `updatedAt` as `revision`, plus at least one changed field. DELETE requires `{revision}`. Field-row locks and monotonic revisions reject stale or competing editors. Structural changes check saved bot graphs, standalone replies and campaign configurations for ID mappings, field names and placeholders. Configured references, including inactive/historical configurations, must be removed first; display-label edits can retain those references. The scan stops with a reconciliation error above 1,000 records per configuration type or excessive legacy nesting instead of silently accepting incomplete evidence.

Changing type validates up to 5,000 existing values against the requested type without rewriting them. Incompatible or larger imported sets require reconciliation. Definitions with cross-business value links cannot be changed or deleted. DELETE preserves nonempty values; clear them first through the contact-value API. An unreferenced definition with only null/empty value rows can be deleted, removing those empty rows and its definition atomically. Audit entries contain resource IDs and changed property names, not entered values.

Ordinary value edits/imports, graph question preparation and template parameter validation hold shared field locks while their transaction uses a definition. Standalone bot-rule saves share the vendor definition lock, so a concurrent name-based configuration cannot slip past the lifecycle reference check. Provider effects are unaffected; no remote API is called by field management.

The source references are ContactCustomFieldController, ContactCustomFieldEngine, ContactCustomFieldRepository and `config/__tech.php`. Native revision checks, safe names/type validation, reference guards and value-preserving deletion differ intentionally from Laravel. Original Blade/DataTables/input/response contracts, plan limits, legacy name/value/configuration reconciliation, bulk migration of large reference/value sets and original deletion equivalence remain unverified. These native tests do not verify a legacy route.

`tests/contact-fields.test.ts` covers both route aliases, malformed/unsafe input, uniqueness and cap concurrency, ownership/revocation, stale edits, existing-value validation, preserved/cleared deletion, graph/template/standalone/campaign dependencies, display-only edits, foreign dependency isolation, corrupt cross-business value links and committed values after a concurrent reader. Existing contact, bot and campaign tests retain regression coverage.
