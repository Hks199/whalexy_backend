# Conversation resolution, reopen and handoff acceptance

The original Laravel resolve, reopen and handoff-accept URLs now have partial Node adapters. They use native bearer authentication and either a single active workspace membership or `X-Vendor-Id`, with `vendor.chats.reply` and assigned-contact visibility. Original cookies, CSRF, encrypted responses, translated messages and live Laravel/frontend/provider comparison remain pending.

| Method | Path                                                            | Behavior                                                                                                                    |
| ------ | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/vendor-console/conversations/:conversationId/resolve`         | Numeric contact ID or UUID, empty JSON body and `Idempotency-Key`; resume paused AI, close the handoff and queue CX scoring |
| POST   | `/vendor-console/conversations/:conversationId/reopen`          | Numeric contact ID or UUID, empty JSON body; reopen the visible contact and return source-named safe fields                 |
| POST   | `/vendor-console/conversations/:conversationId/handoff/accept`  | Numeric contact ID or UUID, empty JSON body; accept one waiting handoff and return the original handoff summary             |
| POST   | `/api/v1/vendors/:vendorId/handoffs/contacts/:contactId/accept` | Native numeric contact ID alias for the same acceptance workflow                                                            |

Reopen clears resolution timestamp/actor but preserves the resolution sequence, existing scores and immutable scoring transcripts. It queues no new analysis and does not resume AI or close a handoff. Phone/email remain masked without phone-view permission; raw contact data and provider identifiers are not returned. This safe projection is narrower than the original raw model response, and native repeated reopen updates the row timestamp.

Acceptance locks the contact and workspace handoff workflow in one transaction. It rechecks current user/vendor status, active membership, reply permission, assignment visibility and API-key revocation/expiry/permission intersection. The contact must be active and native AI must already be paused. Exactly one waiting/accepted handoff must exist; ambiguous imported records require reconciliation. Only a waiting handoff can transition to accepted, so concurrent requests produce one success and one conflict. Assignment, accepting actor and audit event commit together. No customer message or remote AI acknowledgement is invented.

The summary includes the source `uid`, status, reason, severity, request/assignment/acceptance timestamps and assigned/accepting agent display names. Internal open keys and raw metadata are excluded. Caller-supplied actor IDs or automation settings are rejected.

Original acceptance also attempts best-effort AI-provider synchronization to `HUMAN_ACTIVE`; this external synchronization is not implemented by this adapter. Native acceptance leaves the local AI pause intact. The original resolve adapter uses the configured private AI service at `/v1/vendors/:vendorId/conversations/automation` with `customer_phone`, `enabled: true` and `state: AI_ACTIVE`. Provider credentials are sent only in the internal-key header and are not returned or stored in the operation result. If AI is already enabled, resolution needs no remote call.

Resolution requires an `Idempotency-Key` of 8-100 letters, digits, underscores or hyphens. Paused AI also requires `vendor.ai.manage`, deliberately stricter than the original reply permission. A durable operation claim precedes the external call. Successful HTTP/JSON acknowledgement is required; explicit negative acknowledgement, timeout and unknown effects retain an uncertain operation. This is stricter than the original HTTP-success check and has not been verified against a live provider.

After acknowledgement, one transaction rechecks current user/workspace/API-key permissions, contact visibility and the contact revision. It enables local AI, closes the handoff, resolves the contact, freezes the bounded transcript, queues one CX job and completes the operation record. A failed local commit rolls back these local changes and retains the acknowledged operation for reconciliation. Concurrent or new-key retries cannot repeat an unresolved provider call. Already resolved sequences reuse their score instead of queuing another analysis.

HTTP 202 returns the source-named `status`, `message`, `analysis`, `ai_enabled` and `handoff` fields. A completed key replays its saved response; this represents the original request, not the current state after a later reopen. Reusing a key for another conversation fails. Unknown provider effects and changed local state require manual reconciliation; there is no automated recovery endpoint. Billing, imported-history reconciliation, original frontend/session/error behavior and live provider verification remain pending. The existing native local-resolution endpoint keeps its local behavior.
