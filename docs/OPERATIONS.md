# Security and operation

The implementation uses Argon2id password hashes, short signed access tokens tied to database sessions, hashed rotating refresh tokens, reuse detection and database-backed logout. Business ownership is derived from authenticated membership, not request bodies. Each route checks scoped permissions; API key permissions cannot exceed the holder's current membership. Provider credentials and email outbox envelopes use authenticated AES-256-GCM encryption.

Joi validates environment variables and requests. Express has explicit CORS, Helmet, bounded JSON/uploads, request IDs, safe error responses and structured Pino logging. Logs omit authorization, body content, provider credentials and raw provider errors. Media is kept outside public static serving and downloads check owner/business access. Provider calls have timeouts and response bounds; Python runs without a shell, in a private temporary directory, with a time limit.

Raw webhook signatures are checked before JSON parsing. Intake and durable queue records are committed together. Workers atomically claim jobs using PostgreSQL `FOR UPDATE SKIP LOCKED`. Missing handler/configuration is blocked; ambiguous send results and interrupted processing are marked uncertain. Deterministic campaign failures are blocked so they do not prevent subsequent work.

Native Meta Flow mutations persist a canonical request hash, resource identity and operation state before a provider effect. Complete results replay; ambiguous responses and local commit failures retain uncertainty and block another key for that resource. Deterministic preflight and provider client rejections are recorded separately so a corrected request can use a new key. There is no general Graph idempotency guarantee; do not clear uncertain operation rows to force a retry. Provider-backed reconciliation remains incomplete and requires explicit inspection.

WhatsApp signup state is single-use, expires after ten minutes and is bound to the owner, business and session. The backend verifies the exchanged token's app/scopes and actual WABA/phone membership, then reserves phone ownership before subscribing/registering. Only confirmed registration activates encrypted credentials. An uncertain signup retains an encrypted verified token in private idempotency storage and a TOKEN_VERIFIED ownership reservation, while the number remains unavailable for new sends. These records require the same private retention/access controls as integration credentials. No registration PIN is persisted in plaintext. Configure the Meta client callback and complete live app review/provider tests before operational use; coexistence and social-channel signup are not implemented.

The worker evaluates due campaigns and appointment reminders every minute. Appointment reminders require enabled automation and a connected WhatsApp number; multiple connections require an explicit current/contact number. Outside a recipient's incoming-message window, configure an approved reminder template. Unsupported parameters or unavailable recipients/templates create blocked deliveries. Cancellation, rescheduling and disabling automation are checked again before sending. Interrupted outbox jobs and their related reminder/away delivery records are marked uncertain together; reconcile them before retrying. Owners can inspect job metadata and safely retry supported blocked jobs through `/api/v1/vendors/:vendorId/jobs`; central role 1 can use `/api/v1/admin/jobs`. Payloads and credentials are omitted. Uncertain sends and unsupported handlers cannot be retried through these APIs.

WhatsApp requests include their outbox UUID as opaque callback data. Signed status callbacks can confirm an uncertain attempt only when the owning business, sending number, recipient and message snapshot match. The worker preserves a delivered/read callback received before the HTTP send response. Mutation responses that are interrupted, oversized, invalid JSON or HTTP 5xx retain uncertain effects; no automatic resend follows. Callback correlation is tested with signed/local fixtures and mocked provider responses and still needs live Meta verification.

Stripe mutation requests persist a canonical request hash and provider idempotency key before calling the provider. An interruption retries the same key only within 23 hours; later attempts require reconciliation. Open/uncertain checkout sessions block another checkout key. Checkout URLs do not grant access; signed events retrieve the current owned provider session/subscription before activation. Configure STRIPE_SECRET_KEY, BILLING_PLANS and PUBLIC_URL privately. Unknown customer mappings, untracked checkout sessions and incomplete provider ownership retain blocked work.

Resolving a conversation freezes a bounded transcript and queues CX scoring. Completed scores and usage rows are committed atomically. Uncertain or failed analysis requires an explicit audited retry; malformed output cannot repeatedly incur provider work through the worker's normal backoff. GROQ_API_KEY and optional GROQ_CX_MODEL configure analysis. Transcript storage contains customer messages and requires the same retention/access treatment as message history.

The fifth migration adds recipient identity to message logs and backfills it only where the stored raw incoming message proves the sender. Imported messages without such evidence do not open freeform messaging windows. New incoming messages populate the identity; approved templates remain available outside the window. This avoids treating mutable contact metadata or outgoing activity as customer consent to freeform messaging.

The sixth migration adds the source contact marketing opt-out flag (1 or null) and a campaign queue index. Audience IDs and recipient numbers are snapshotted at the first due dispatch; contact values are rendered in bounded batches. Marketing consent is rechecked before sending, including duplicate identities. Paused sends defer without consuming retry attempts. Cancellation stops unsent work; a provider request already in progress can still be accepted. Queue status 1 means awaiting preparation, 3 means prepared/awaiting delivery, 4 means sent and 2 means terminal failure/skip/cancellation. Campaigns finish as completed or completed_with_errors. Blocked/uncertain jobs still require reconciliation and have no automatic resend path.

Legacy password verification supports bcrypt 2a/2b/2y with costs 4 through 14 and passwords up to 72 UTF-8 bytes, and bounded Argon2id hashes. Other algorithms, oversized inputs and higher work factors require password reset. Login accepts existing short passwords while registration/reset continue to require at least 12 characters. Migrated accounts still need verified email/phone and correctly imported memberships; this adapter does not certify the reconstructed users schema. Bcrypt compatibility was checked against the installed library and its [upstream API documentation](https://github.com/dcodeIO/bcrypt.js/).

Before running publicly, configure HTTPS termination, exact CORS/public URLs and the correct trusted proxy hop count. Rate limits currently use process-local storage; use a shared gateway/store before running multiple API replicas. Set up log retention, database backups and restoration tests, encryption-key backup, monitoring of failed/blocked/uncertain jobs, and provider reconciliation. Keep `.env`, `.env.test` and `.local` out of version control.

This checkout has not had an independent penetration test. Live OAuth, provider contracts, complete subscription/billing enforcement, upload scanning/quotas, comprehensive administrative operations and the original database migration remain unfinished. See `migration/FEATURE_PARITY.md`; passing Node tests does not close those gaps.

Database migrations are versioned in `prisma/migrations`. Do not edit an applied migration. The supplied SQLite snapshot has been copied into the separate legacy_archive PostgreSQL schema with exact tagged row values and read-back hashes. This archive contains sensitive source records, including credentials and historical tokens; access is restricted to the database owner and it is not exposed through application APIs. It does not activate source accounts, memberships, tokens or provider jobs. The separate whalexy_import_validation database verifies explicit native transformations and owner memberships, with unresolved records retained in its private legacy_import.quarantine table. It contains source secrets even though none are activated; restrict access like the archive. Import validation does not overwrite the application database, fabricate verification or start legacy campaigns/flows. Run npm run db:audit-source to refresh the metadata-only audit, npm run db:archive-source to verify/recreate the archive idempotently, or node scripts/native_sqlite_import.mjs --verify for native field/membership/quarantine read-back checks. See migration/SQLITE_DATABASE_REVIEW.md.
