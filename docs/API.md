These are new API contracts. They do not preserve Laravel URL or response compatibility. Authentication is `Authorization: Bearer <accessToken>`. Business-scoped API keys use `Authorization: ApiKey <token>` and the intersection of key permissions and the user's current business permissions.

Exact paths and permissions are defined in `src/modules/<feature>/<feature>.routes.ts`; request schemas live in the corresponding validation files. Use the [feature index](FEATURE_INDEX.md) to find the router, controller, workflow and tests. Unsupported routes return 404. Body validation rejects unknown properties. API errors use `{ "error": { "code": "...", "message": "..." } }` with field validation details when applicable. List APIs cap page sizes at 100. Contact visibility depends on membership permissions and assignment.

Blog create/update uses title, excerpt, content, optional slug/authorName/locale/categoryId/tagIds, intent (draft/preview/publish/schedule), scheduledAt and SEO fields. Schedule requires a future date; the worker publishes due articles once per minute. Business membership permissions never confer central CMS access. Existing roles are checked on each request. These JSON routes do not render Laravel Blade views; CMS image uploads, original response contracts and full source HTML/style/embed behavior remain pending.

Bot flow definitions contain title, enabled, triggerType, startTrigger, phoneNumberId and graph. Graphs contain start_node (source start_node_id is also accepted) and nodes with id, type, payload and next_node; source payload.next_node is normalized. Message, question, interactive button/list, goto, custom_field, wait, stay_in_session and terminal team_assignment nodes execute on WhatsApp. A custom_field node requires an owned custom_field_id, its input name as custom_field_name and question_text. Question variables are stored in the bounded conversation session; custom-field answers also update the contact record. Repeating an explicit start keyword resets the flow and its variables. Sessions are isolated by business, number and contact and expire after 24 hours, with delayed-session expiry described below. Live interactive IDs are unique per prompt; previews use graph choice IDs. Exports/clones default to disabled. Other node types may be saved as drafts but cannot be activated. Legacy canvas/database reply exports and social channel execution still require conversion. Generic resources/bot-flows writes are disabled to prevent bypassing graph validation.

Wait nodes also execute: payload.wait_time is an integer from 1 to 604800 seconds, with optional wait_message or text. The next node is scheduled in PostgreSQL; incoming messages do not bypass the delay, but repeating the explicit start keyword restarts the flow. A waiting session remains valid until 24 hours after its scheduled continuation. Timers recheck the recipient, flow revision, business/contact state, handoffs, timing and out-of-office settings. Timing/away pauses retry without consuming attempts; freeform sends still require the recipient's open 24-hour WhatsApp window. Continuations produce messages and the next timer atomically, with a durable receipt that supports safe recovery after interruption. Previews show the proposed delay and do not schedule jobs.

Terminal team_assignment nodes accept assigned_team_member (the user's uid), assignment_message and optional assigned_team_member_name. The user must be an active business member with messaging permission. Execution assigns that user, disables AI and creates a waiting handoff with reason bot_flow_team_assignment. Its acknowledgement may be sent while the handoff is open; revoked agent access or a transferred/resolved handoff prevents stale delivery. Automation after a team-assignment node remains unsupported, so enabling an assignment with a next node is rejected.

Webhooks acknowledge durable receipt, not completion of all processing. Unsupported event types remain blocked for investigation. A queued message response does not mean delivery; provider statuses reconcile later. `uncertain` outbox jobs require provider reconciliation before retrying to avoid duplicate external effects.

Contact create/update accepts an optional phoneNumberId belonging to a connected WhatsApp credential in that business. An already scoped contact cannot move to another business number. CSV import accepts phoneNumberId and/or groupId, inherits a scoped group's number and rejects mismatches. Identical customer numbers are deduplicated within their business-number scope. DELETE requires vendor.contacts.delete and contact visibility; a configured campaign test recipient, future active booking or processing send returns 409. Pending/blocked sends and timers are cancelled transactionally with linked-record cleanup.

The manual store connection accepts integrationId linking an existing active Shopify/WooCommerce integration with matching business and hostname; an unmapped connection can receive signed receipts but its processing remains blocked. Supported Shopify topics are orders/create, orders/updated, orders/paid, orders/fulfilled and orders/cancelled; WooCommerce supports order.created and order.updated. Topic and delivery identity are retained with the signed body. Reusing a delivery/event ID with a changed payload returns 409. Remote webhook registration remains pending.

Configure native text notifications with `GET/PUT /api/v1/vendors/:vendorId/integrations/stores/:provider/:integrationId/notifications`, where provider is shopify or woocommerce. Settings contain enabled, phoneNumberId and rules. Each rule selects type, templateId, bodyParameters and headerParameters. Values select exactly one literal, orderField or contactField and optional fallback; supported order fields are orderNumber, orderId, customerName, total, currency, status, trackingNumber and trackingUrl. Types are order_confirmation, payment_confirmation, shipment_tracking, order_cancelled, refund_processed, order_processing, order_completed, order_on_hold and order_failed. Templates and senders must belong to this business. Rules only enqueue notifications for transitions observed after configuration; enabling a rule does not resend historical orders. A once-per-order/type receipt prevents duplicates. Missing/invalid international customer phones, disabled settings, cancelled orders, changed templates and marketing opt-outs suppress dispatch. Template parameter counts must match the approved text template. Rich headers/buttons and source legacy notification settings require conversion.

Stripe supports customer.subscription.created/updated/deleted for a uniquely mapped local customer. With STRIPE_SECRET_KEY, subscription and invoice events retrieve current provider state; tracked checkout completion/payment/expiry events reconcile the owned session first. Without credentials, only signed complete subscription snapshots are processed and conflicting same-second revisions remain blocked. Unknown/ambiguous customers and untracked checkout identities retain blocked jobs. Only existing paid add-ons linked to that subscription are changed; incoming metadata cannot create an add-on entitlement. Central manual review accepts only pending records. Administrator overrides remain separate from paid add-ons, and neither alone bypasses the active base-plan requirement for AI replies.

Checkout takes a planId from server-controlled BILLING_PLANS; client-supplied prices, customers, amounts and return URLs are rejected. Checkout/portal Idempotency-Key must contain 8–128 alphanumeric, underscore or hyphen characters. A pending/open checkout blocks another key; interrupted requests use their persistent Stripe key for up to 23 hours. Checkout response is a redirect URL, not proof of payment. Existing subscriptions are managed through the portal. Configure matching recurring Stripe prices and PUBLIC_URL before use. Invoice reads are customer-scoped and currently return the first 100 records with hasMore.

Classification PATCH accepts attribute (intent, sentiment, urgency or risk_level) and value (source preset, owned custom tag or null). Changes append history; an unchanged value creates no duplicate history. Contact resolution queues CX scoring against a frozen first-10/latest-50-message transcript. GET /cx-scores/:id returns that snapshot with the score; customer replies reopen the conversation and the next resolution gets a new sequence. GROQ_API_KEY is required for analysis. Results derive ratings locally from validated 0–10 scores and record usage once. Failed/blocked/uncertain analyses require the dedicated retry endpoint. Active analyses cannot be retried.

WhatsApp sends carry the job UUID as biz_opaque_callback_data. Signed status callbacks can reconcile a processing/uncertain job only when business, sender number, recipient and original message identity agree. A known provider identifier prevents a resend. Job listings expose metadata only; retrying unsupported handlers or ambiguous message effects returns 409.

Media sends use kind=media and media={type,url,caption?,filename?}. Types are image, video, document and audio. URLs must use HTTPS on a DNS hostname with no credentials, fragment or custom port; literal IPs and local/internal/reserved hostnames are rejected. The provider retrieves the URL; the backend does not download it. Captions are limited to 1024 characters and are forbidden for audio. Filenames are allowed only for documents and cannot contain directory separators or controls. Graph media_message nodes use media_type, media_url, caption and filename with the same limits; captions support conversation variables. Private local uploads, provider media IDs and Meta uploads still need an upload/ownership adapter. All media sends require the current recipient's WhatsApp service window and recheck identity/number scope before dispatch.

Flow messages use `kind=flow` and `flow={id,body,cta?}` on the message send endpoint. They require an owned published provider flow and the recipient's open incoming-message window. Static flows launch their first screen from the locally fetched/uploaded JSON; endpoint-backed flows require the provider endpoint URI and launch data_exchange. Flow messages use a generated token bound to contact, flow and business number, expiring after 24 hours. Submitted nfm_reply responses are recorded only for matching unconsumed native tokens. Unknown historical tokens remain in raw incoming message history and require legacy reconciliation; they are not assigned to a flow from untrusted answer fields. Template flow launches outside the customer window and dynamic encrypted business actions remain pending; native encrypted screen routing is documented in FLOW_AND_CATALOG.md.

Meta Flow creation returns a provider draft container; upload JSON separately using PUT /:flowId/json with `{flowJson}` before publishing. Meta validates component semantics; native validation rejects oversized/malformed screen definitions and duplicate identifiers before provider effects. Published flows cannot be edited/deleted; deprecate them instead. Mutation keys are persisted and complete results replayed. Uncertain/processing operations require reconciliation and block another key for that resource. Actual phone membership is checked using the selected WABA's phone list before every flow operation. Sync imports only flows returned by that WABA and rejects conflicting native business ownership. Asset fetches allow only graph.facebook.com and lookaside.fbsbx.com; previews allow only business.facebook.com. Reads require a sync/creation ownership record first. Fetching a definition populates the native launch cache and invalidates older queued revisions.

WhatsApp signup requires server META_APP_ID, META_APP_SECRET and META_SIGNUP_CONFIG_ID. Start returns a Meta authorization URL/state and a fixed PUBLIC_URL/integrations/meta/callback return URI; the client must handle that route and forward the authorization code to the completion endpoint using its authenticated session. This client integration is not implemented in the original Blade frontend. Completion also requires the selected WABA/phone IDs and six-digit registration PIN. State expires in ten minutes, is consumed before code exchange and cannot be used from another account/session. Provider app identity, token validity/scopes and phone membership are checked before registration. Credentials and retained failed-signup tokens are encrypted and omitted from API responses. Failed/uncertain registration does not activate the number; a new signup does not bypass an unresolved registration operation. Social-channel signup, coexistence and full reconciliation are separate remaining workflows.

Provider request formats were reviewed against the original PHP services and Meta's first-party [WhatsApp API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) and [embedded signup collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/du6gzjv/embedded-signup). Native tests use mocked Graph responses; this is not a live provider compatibility certification.

Pending accounts can request a fresh email proof through resend-verification using their current email/password. There is a 60-second per-account cooldown. The new challenge replaces all previous codes/proofs atomically; concurrent resends leave one active challenge. This also refreshes the email proof needed to finish phone verification, so verify the new email code before calling phone/start or phone/verify. Fully verified accounts receive ALREADY_VERIFIED. No login session is issued by resending. Email jobs skip consumed/expired/superseded challenges and changed account destinations.

New campaigns default to requireTest=true and status awaiting_test. Queue the test through `POST /api/v1/vendors/:vendorId/campaigns/:id/test` with an Idempotency-Key and optional contactId; otherwise the source test_recipient_contact setting selects the test contact. The endpoint requires campaign-send and chat-reply permissions. A provider-acknowledged test releases the campaign to scheduled; cancellation and stale configuration/templates prevent release. Test logs are retained separately from audience reports. requireTest=false needs vendor.campaigns.skip_test and is audited. Historical native configurations without requireTest keep their existing scheduling behavior. Template values select exactly one literal/contactField/customFieldId and an optional fallback.

Bot session nodes retain earlier menus and support scoped preview selections, exit and reset. See [session behavior](BOT_SESSIONS.md) for commands, token invalidation and limits.

Bot questions support owned unique `store_in_field` mappings, typed answer validation, optional answers, ordered equals/contains/starts-with/numeric conditions and explicit default or terminal targets. Previews use current field types without saving answers; downstream template custom-field parameters use the newly validated answer. See [question behavior](BOT_QUESTIONS.md) for payload fields, validation differences and unconverted regex/canvas contracts.

Contact create/edit accepts an existing `countryId` or null. Custom-value edits validate current owned field types atomically. Contact CSV import accepts country/group/custom-field columns and source aliases; `GET /contacts/export?extended=true` exports those columns with visibility and phone privacy guards. See [contact data workflows](CONTACT_DATA.md) for formats, limits, permissions and pending Excel/source compatibility.

Custom-field definitions use `/api/v1/vendors/:vendorId/custom-fields` and the guarded `/resources/custom-fields` alias. PATCH and DELETE require the current `updatedAt` as `revision`; POST accepts `inputName`, supported `inputType` and optional display `name`. Referenced fields and populated/incompatible/cross-business values are protected. See [field management](CONTACT_FIELDS.md) for permissions, caps, reference checks and legacy differences.

Native bot graphs execute selected approved `whatsapp_template` nodes through the guarded outbox. See [template node inputs and remaining gaps](BOT_TEMPLATES.md).

Bot graph `catalog` nodes support single, multiple and full-catalog delivery. See [catalog node inputs and dispatch guards](BOT_CATALOGS.md).

Bot graph `whatsapp_flow` nodes launch published static/native encrypted forms with graph-bound response tokens. See [Meta Flow node inputs and remaining gaps](BOT_META_FLOWS.md).

Standalone reply-button/list/CTA URL/location-request messages use `POST /api/v1/vendors/:vendorId/messages/send` with `kind: "interactive"` and an `interactive` object. Native graphs also support CTA nodes with fixed destinations and automatic continuation. The existing contactId, phoneNumberId, Idempotency-Key and reply permission requirements apply. See [payloads, choice correlation and limits](INTERACTIVE_MESSAGES.md).

Reactions use the same endpoint with `kind: "reaction"` and `reaction: {messageId,emoji}`. The target is a native owned message ID; an empty emoji removes your reaction. See [queued send/remove, incoming state and reconciliation limits](REACTIONS.md).
